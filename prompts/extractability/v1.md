You decide whether a Pull Request contains enough evidence to reconstruct a
functional software requirement.

A functional requirement describes a behaviour, capability, or response that
the system must provide or guarantee. Examples of reconstructable behaviour:
a new capability offered to users, a changed system response, a corrected
behaviour that users can observe, a new validation rule the system enforces.

Answer NOT_EXTRACTABLE when the Pull Request describes only:
- purely internal refactoring with no observable change in behaviour;
- infrastructure, build, or dependency updates;
- documentation, comments, or typo fixes;
- test-only changes;
- type annotations or static-analysis fixes that do not change behaviour;
- changes whose description is too vague to determine any specific behaviour.

Judge only the evidence given in the title and body. Do not assume behaviour
that is not described. A Pull Request that merely sounds important is not
extractable if the concrete behaviour cannot be determined.

## Examples

Title: "Add CSV export to the reports page"
Body: "Users asked to download their reports as CSV. This adds the export
button and the endpoint behind it."
{"extractability": "EXTRACTABLE", "reason": "Adds a user-facing export capability."}

Title: "Fix typo in cmdline.py comment"
Body: "Changes 'a argument' to 'an argument'. No code logic is affected."
{"extractability": "NOT_EXTRACTABLE", "reason": "Comment-only change with no behavioural effect."}

Title: "Refactor the parser to simplify the internal class hierarchy"
Body: "Splits the Parser class into three smaller classes. Behaviour is unchanged."
{"extractability": "NOT_EXTRACTABLE", "reason": "Internal refactoring with no observable behaviour change."}

## Output

Reply with a single JSON object and nothing else. No preamble, no explanation
outside the JSON, no markdown code fences.

{"extractability": "EXTRACTABLE" | "NOT_EXTRACTABLE", "reason": "<one short sentence>"}
